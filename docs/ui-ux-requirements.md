# Jikan UI/UX 再設計：課題定義と要求分析

## 1. 前提と対象範囲

Jikan は、ナレッジワーカーがターミナルから作業時間を記録・整理し、振り返るための CLI である。ここでいう UI は Web 画面ではなく、コマンド、引数、対話プロンプト、標準出力を指す。

現行実装で確認できる機能は、計測の開始・停止、稼働状況の確認、記録の一覧・編集・削除、プロジェクトとタグの管理である。一方、`switch`、`report`、`export` は未実装である。

### 想定ユーザー

- 複数案件を並行し、日中に何度も作業を切り替える開発者
- ターミナルを日常的に利用し、記録作業は本業を中断しない短さで済ませたい人
- 週次または月次に、プロジェクト・タグごとの時間を確認して、働き方の改善に使いたい人

## 2. 課題定義

### ユーザーが達成したいこと

ターミナルユーザーが「作業の開始・切替・終了を忘れず、あとから作業時間の内訳を信頼して確認できる」状態を、操作の負担なく作る。

### 現状の体験上の課題

| 観測できる現状 | ユーザーへの影響 | 設計上の課題 |
| --- | --- | --- |
| `start` はプロジェクト ID を受け取るが、タグは開始時に指定できない | 文脈情報を後編集するか、記録を諦める | 開始時の分類入力が不足している |
| 実行中に別作業へ移る `switch` が未実装 | stop → start の手順を忘れやすく、重複計測エラーにもなる | 最頻出の切替フローが途切れている |
| `list` はプロジェクト ID と日時中心で、タグ・所要時間・実名プロジェクトを表示しない | 一覧から何にどれだけ使ったか判断できない | 振り返りに必要な情報設計がない |
| `report` と `export` が未実装 | 集計・請求・自己レビューにデータを使えない | 記録から意思決定につなげられない |
| 成功時は開始/停止時刻のみを主に返す | 正しい案件・タグで記録できた確信を持ちにくい | 操作結果のフィードバックが弱い |

### 解くべき優先課題

1. **記録の摩擦を下げる**：開始、停止、切替を少ない入力と明確な結果表示で完了させる。
2. **記録の文脈を保つ**：開始時点でプロジェクト・タグを無理なく付与し、間違いをすぐ修正できるようにする。
3. **記録を振り返りに変える**：期間・プロジェクト・タグで、時間の内訳と合計を読めるようにする。

### 成功指標（計測可能な仮説）

- 計測開始から完了まで、通常ケースは 1 コマンド・5 秒以内
- 作業切替は 1 コマンドで完了し、同時に実行中の記録が 2 件にならない
- 一覧またはレポートだけで、指定期間の案件別合計時間を確認できる
- 開始・切替・編集後の出力で、対象タイトル、プロジェクト、タグ、開始/終了時刻を確認できる

## 3. JTBD（Jobs To Be Done）

### メインジョブ

**複数の作業を行き来しているとき、今から行う作業を素早く記録し、終わったら正確に止めたい。そうすることで、記憶に頼らずに実際の時間配分を把握したい。**

### 関連ジョブ

| 状況 | したい進歩 | 期待する成果 |
| --- | --- | --- |
| 作業を始める直前 | 作業名と分類を残してタイマーを始める | 後から見ても何の時間か分かる |
| 割り込みや案件変更が起きたとき | 現在の計測を安全に終え、次の計測へ移る | 重複や未停止を生まない |
| 終業時・週次レビュー時 | 記録漏れや誤分類を直す | 信頼できる履歴になる |
| 請求・見積もり・改善をするとき | 案件・活動別の合計を読む／外部へ渡す | 次の判断に使える数字を得る |

### 避けたいこと

- ID を調べたり、長い日時を何度も入力したりして作業の集中を切らすこと
- 「いま何を計測中か」「正しく分類できたか」が分からないこと
- 終了後にスプレッドシートへ転記して集計し直すこと

## 4. AI に実装させるべきプロダクト要求

AI への実装依頼は、画面を追加することではなく、以下の CLI 体験を一貫した仕様として実装することにする。既存のコマンド互換性を原則維持し、破壊的変更が必要な場合は移行案を添える。

1. **コンテキスト付き計測**：`start` でタイトル、プロジェクト、複数タグを指定できる。利用者が ID を覚えなくてよい名前指定と、シェルの Tab 補完による候補提示を提供する。
2. **原子的な切替**：`switch` で実行中の記録を停止し、新しい記録を開始する。成功時に両方の結果を明示し、失敗時に中途半端な状態を残さない。
3. **振り返り可能な一覧**：`list` に所要時間、プロジェクト名、タグ、状態を表示し、少なくとも期間・プロジェクト・タグで絞り込めるようにする。
4. **期間レポートとエクスポート**：`report` で期間内の合計とプロジェクト別／タグ別内訳を表示し、`export` で同じ対象を CSV 等の機械可読形式で出力する。
5. **安心できるフィードバック**：すべての変更操作は、何が記録・変更されたかを簡潔に返す。入力不備は、原因、修正方法、例を含むエラーにする。

優先順位は **計測（1・2）→ 確認と修正（3・5）→ 活用（4）** とする。レポート・エクスポートより先に、正確な入力と切替を成立させる。

## 5. ユーザーストーリーと受け入れ条件

### US-01：作業を始めるとき、内容を添えてタイマーを開始する

**ターミナルで作業を始める人として、`jikan start` を打つときにタイトル・プロジェクト・タグを一度に指定して計測を始めたい。あとで一覧を見たときに、何をしていた時間なのかを思い出したり入力し直したりせずに済ませるためだ。**

受け入れ条件：

- `start` はタイトル、プロジェクト、0 件以上のタグを同時に受け付ける。
- プロジェクト・タグは ID に加え、名前で選択できる。名前が曖昧または存在しない場合、候補または次の操作を示して開始しない。
- `--project` と `--tag` の値を入力中に Tab を押すと、登録済みのプロジェクト名・タグ名を候補として表示し、選択できる。タグは複数指定時にも補完できる。
- 補完候補は、実行時にローカルの SQLite データベースから取得する。候補がない場合でもコマンドは異常終了しない。
- 初回利用者には、使用中シェル向けの補完有効化コマンドと、補完を有効化済みか確認する手順を案内する。
- 開始成功時には、記録 ID、タイトル、プロジェクト名、タグ、開始時刻を表示する。
- 既に実行中の記録がある場合、二重に開始せず、実行中の記録を特定できる情報と `switch`／`stop` の案内を表示する。

### US-02：別の作業に移るとき、計測を切り替える

**ターミナルで別のタスクに移る人として、割り込みやレビュー依頼が来たときに `jikan switch` だけで今の計測を終え、次の作業を始めたい。`stop` と `start` を別々に打つ間の停止忘れや、二重計測を防ぐためだ。**

受け入れ条件：

- `switch` は新しいタイトル、プロジェクト、タグを受け取り、実行中の記録が 1 件なら終了時刻を設定して新しい記録を開始する。
- 成功時には停止した記録と開始した記録のタイトル・時刻・分類を表示する。
- 実行中の記録がない場合は、新しい記録だけを開始し、その旨を表示する。
- 新規記録の入力検証または保存に失敗した場合、元の記録を停止しない（原子性）。
- 完了後、実行中の記録は必ず 0 件または 1 件であり、切替成功時は新規記録だけが実行中である。

### US-03：退勤前に、動いているタイマーを確認して止める

**ターミナルで仕事を終える人として、`jikan status` で今の計測内容と経過時間をすぐ確認し、`jikan stop` で確実に止めたい。計測を動かしたまま席を離れていないと自信を持つためだ。**

受け入れ条件：

- `status` は実行中のタイトル、経過時間、開始時刻、プロジェクト名、タグを見出し付きで表示する。
- 実行中の記録がない場合は、エラーではなく空状態と開始コマンド例を表示して正常終了する。
- `stop` 成功時には、停止した記録のタイトル、終了時刻、確定した所要時間を表示する。
- `stop` 対象がない場合は、記録を変更せず、理由と `status` の確認方法を表示して非 0 で終了する。

### US-04：終業時に、間違えた記録を見つけて直す

**ターミナルから履歴を見直す人として、終業時に `jikan list` で記録を探し、間違えた時間・プロジェクト・タグを `jikan edit` で直したい。請求や振り返りに使える、信頼できる履歴にするためだ。**

受け入れ条件：

- `list` は ID、日付、タイトル、所要時間、プロジェクト名、タグ、実行中/完了状態を表示する。
- `list` は少なくとも期間、プロジェクト、タグで絞り込める。指定条件は出力にも明示する。
- `edit` は開始・終了時刻、プロジェクト、タグを変更でき、終了時刻が開始時刻より前になる変更を拒否する。
- 編集成功時には変更後の主要項目を表示する。タグ追加・削除で対象が不正な場合は、変更を保存しない。

### US-05：月末に、案件ごとの作業時間を集計する

**ターミナルで週次・月次の作業時間を確認する人として、`jikan report` で案件・タグ別の合計を確認し、必要なら `jikan export` で取り出したい。表計算ソフトへ手で転記・集計せず、請求や次の見積もりに使うためだ。**

受け入れ条件：

- `report --from DATE --to DATE` は対象期間、総計時間、プロジェクト別合計、タグ別合計を表示する。
- 日付境界とタイムゾーンは設定値に従い、出力に適用した期間・タイムゾーンを表示する。
- 未分類の記録は「未分類」として集計に含め、総計と内訳に不一致を生まない。
- `export` は同じフィルタ条件を受け取り、CSV など機械可読な形式で ID、開始・終了、所要時間、タイトル、プロジェクト、タグを出力する。
- 対象データがない場合は、空であることと対象条件を表示し、エラーにはしない。

## 6. 非機能・UX 原則

- **速さ**：通常の計測操作は対話なしでも完結し、対話は曖昧さを解消するときだけ使う。
- **発見可能性**：ID や完全な名称を覚えさせず、プロジェクト・タグはシェルの Tab 補完で選べる。補完の初回設定方法は `--help` または専用コマンドから見つけられるようにする。
- **一貫性**：日時形式、タイムゾーン、成功・警告・エラーの表現を全コマンドで統一する。
- **安全性**：削除・アーカイブ以外の操作も、データの中途半端な更新を残さない。削除確認では対象の要約を先に示す。
- **スクリプト適性**：人間向けの Rich 表示に加え、レポート・エクスポートはパイプしやすい安定した形式を持つ。
- **アクセシビリティ**：色だけに依存せず、状態をテキストでも表現する。

## 7. 要件確定前に検証する仮説

- 最多利用者が ID 入力より名前入力・候補選択を望むかを、5 人程度のタスクテストで確認する。
- タグは開始時に必須にすべきではなく任意で十分かを、開始記録の分類率で判断する。
- レポートの最初の軸はプロジェクト別・タグ別で足りるか、顧客別や請求単位が必要かを利用者インタビューで確認する。
