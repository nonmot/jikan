# Jikan E2E受入テストシナリオ

## 1. 目的と対象

この文書は、[UI/UX 要件](ui-ux-requirements.md) と [ユーザーフロー](user-flow-mvp.md) を、CLI を実際に起動して検証できる受入テストに変換するための仕様である。単体テストではなく、コマンドの終了コード・標準出力・SQLite 上の最終状態を一連で確認する。

対象は `init`、分類管理、計測の開始・切替・確認・停止、ライブタイマー、一覧・編集、レポート、CSV 出力である。GUI、クラウド同期、チーム共有は対象外とする。

なお、第 3 節はプロダクト要件に対する完成時の受入シナリオである。第 4 節では、現行実装（`9b1fcf8` 時点）だけでパスさせられるシナリオを分離する。

## 2. 実行環境と共通規約

### 隔離環境

- 現行実装は `Path.home() / ".jikan"` を保存先に使うため、各シナリオの子プロセスには空の一時ディレクトリを `HOME` として渡す。`JIKAN_HOME` は現時点では未対応である。
- タイムゾーンは `Asia/Tokyo` に固定する。日付境界の確認は RPT-02 で扱う。
- 現在時刻を必要とするテストでは、テスト用の時計を固定または注入できるようにする。待機時間に依存して所要時間を検証しない。
- 実行ごとに `jikan init` を行い、プロジェクト `client-web`、`jikan`、タグ `development`、`frontend`、`review` を作成する。ただし、空状態を検証するケースは作成前に実行する。

### 確認方法

各ケースで次の三点を確認する。

1. CLI の終了コードと出力（成功・失敗の理由、次の操作を含む）。
2. `jikan status`、`list`、`report`、`export` から利用者に見える結果。
3. SQLite のエントリー数、実行中エントリー数、開始・終了時刻、プロジェクト、タグ。表示だけで検出できない原子性や重複を確認するために用いる。

出力の日時・ID は可変値なので完全一致にはせず、固定時計を使うか、必要なフィールド・形式・相対関係を検証する。色や罫線の種類ではなく、テキストと意味を検証する。

### ライブ表示の実行方法

`timer` は疑似端末（PTY）で起動する。出力をキャプチャし、初回描画、1 秒以上後の再描画、`Ctrl+C` 送信後の状態を検証する。端末サイズは標準サイズ（80×24）と小サイズ（40×12）を使う。

### 現行E2Eの不変条件

- CUR-05〜CUR-09 は、各コマンドの後に SQLite を読み、`end_at IS NULL` の件数が 0 または 1 であることを確認する。
- CUR-06 は、失敗後に実行中の ID・タイトル・開始時刻が操作前と一致することを確認する。
- CUR-08 は、`end_at >= start_at` と所要時間の正値を確認する。実時間を固定しない現状では、停止時刻の完全一致は要求しない。
- CUR-11 のタグ操作は名称ではなく ID を使う。現行CLIのオプションは `--add-tag ID` と `--remove-tag ID` である。

## 5. 完成時のシナリオ詳細

### SET-01：初期化と分類の登録

**前提**：空の `HOME`（将来 `JIKAN_HOME` を導入する場合は、その隔離先）。

**操作**：`jikan init` を実行後、`project add` で `client-web` と `jikan`、`tag add` で `development`、`frontend`、`review` を登録する。

**期待結果**：すべて正常終了し、同名のプロジェクト・タグを一覧または補完候補から確認できる。DB は作成されるが、エントリーは 0 件である。

### STR-01：分類付きで開始する

**前提**：SET-01 完了、実行中のエントリーなし。時計を `2026-10-21 09:00:00 JST` に固定する。

**操作**：`jikan start --title "ログイン画面の実装" --project client-web --tag development --tag frontend` を実行する。

**期待結果**：

- 正常終了し、ID、タイトル、`client-web`、2 個のタグ、開始時刻を表示する。
- 実行中エントリーは 1 件だけで、タイトル・プロジェクト・タグ・開始時刻は出力と一致する。
- `status` で同じタイトル・分類を確認できる。

### CMP-01：プロジェクト・タグを補完する

**前提**：SET-01 完了。対象シェルの補完を有効化済み。

**操作**：対話可能なシェルで `jikan start --project cli<Tab>`、続けて `jikan start --project client-web --tag f<Tab>` を実行する。複数タグ指定後にも `--tag r<Tab>` を実行する。

**期待結果**：最初の補完候補に `client-web` を含む。タグは `frontend`、その後のタグは `review` を候補として返す。候補の取得失敗や候補なしの場合でも、補完処理がシェルを異常終了させない。

### STR-02：未分類で開始する

**前提**：実行中のエントリーなし。

**操作**：`jikan start --title "メール整理"` を実行する。

**期待結果**：正常終了し、プロジェクトとタグが未設定の実行中エントリーを 1 件作成する。未設定であることを出力で判別できる。

### STR-03：存在しない分類で開始する

**前提**：実行中のエントリーなし。

**操作**：存在しない `--project` または `--tag` を指定して `start` を実行する。

**期待結果**：非 0 で終了する。存在しない分類名と、登録または候補確認の方法を表示する。エントリーは作成されず、実行中件数は 0 のままである。

### STR-04：実行中に再度開始する

**前提**：STR-01 により #42 が実行中。

**操作**：別タイトルで `jikan start` を実行する。

**期待結果**：非 0 で終了する。#42 のタイトルと開始時刻を示し、`jikan switch ...` と `jikan stop` を案内する。#42 は実行中のままで、新規エントリーは作成されない。

### SWT-01：実行中のタスクを切り替える

**前提**：#42（`ログイン画面の実装`、`client-web`、`development`、`frontend`）が実行中。時計を `09:42:18 JST` に固定する。

**操作**：`jikan switch --title "PR #43 のレビュー" --project jikan --tag review` を実行する。

**期待結果**：正常終了し、停止した #42 と開始した新規記録の内容を表示する。#42 の終了時刻は `09:42:18 JST`、新規記録の開始時刻も同時刻である。実行中は新規記録 1 件だけである。

### SWT-02：実行中なしで切り替える

**前提**：実行中のエントリーなし。

**操作**：有効なタイトル・分類で `jikan switch` を実行する。

**期待結果**：正常終了し、「停止対象なしで新規開始した」ことを表示する。新規記録が 1 件だけ実行中である。

### SWT-03：不正入力で切替に失敗する

**前提**：#42 が実行中である。

**操作**：存在しないプロジェクトまたはタグで `jikan switch` を実行する。

**期待結果**：非 0 で終了する。#42 の `end_at` は `NULL` のままで、開始時刻・分類も変わらない。新規エントリーは作成されない。

### STS-01 / STS-02 / STP-01 / STP-02：確認と停止

| ID | 前提と操作 | 期待結果 |
| --- | --- | --- |
| STS-01 | 分類付きの実行中記録で `status` | タイトル、プロジェクト、タグ、開始時刻、正の経過時間を見出し付きで表示し、正常終了する。 |
| STS-02 | 実行中なしで `status` | 空状態と `start` の例を表示し、正常終了する。 |
| STP-01 | 時計を固定した実行中記録で `stop` | タイトル、終了時刻、確定所要時間を表示し、DB の `end_at` が固定時刻になる。以後の `status` は空状態。 |
| STP-02 | 実行中なしで `stop` | 非 0 で終了し、停止対象なしと `status` の確認方法を表示する。DB の既存データを変更しない。 |

### TMR-01：ライブタイマーを表示する

**前提**：タイトル `PR #43 のレビュー` の実行中記録がある。PTY は 80×24。

**操作**：`jikan timer` を起動して初回描画を取得し、1 秒以上待機して再描画を取得する。

**期待結果**：

- 両方の描画に現在のタスクを表す見出し、タスク名、`Ctrl+C` で閉じる案内がある。
- 時計は `HH:MM:SS` を表し、少なくとも 5 行の文字セルを使用している。
- 2 回目の時計は 1 秒以上進んでいる。
- 表示中も DB のエントリー内容・実行中状態は変更されない。

### TMR-02：ライブタイマーを閉じても計測を継続する

**前提**：TMR-01 と同じ。

**操作**：`timer` に `Ctrl+C` を送信し、プロセス終了後に `status` を実行する。

**期待結果**：`timer` は正常終了する。`status` は同じエントリーを実行中として返し、経過時間は `timer` 起動前より進んでいる。`end_at` は `NULL` のままである。

### TMR-03：ライブタイマーの空状態・狭い端末

| 前提と操作 | 期待結果 |
| --- | --- |
| 実行中なしで `jikan timer` | ライブ表示を開始せず、`start --title` の例を含む空状態を表示して正常終了する。 |
| 実行中が複数件で `jikan timer` | ライブ表示を開始せず、データ異常を示して非 0 で終了する。 |
| 40×12 の PTY で長いタイトルの `jikan timer` | プロセスが異常終了せず、経過時間が表示される。タイトルは折り返しまたは省略されてよい。 |

### LST-01：一覧と絞り込み

**前提**：期間内に、完了済みの `client-web`（タグ 2 件）、完了済みの `jikan`（タグ 1 件）、実行中の未分類記録を作成する。

**操作**：全件、期間、プロジェクト、タグの各条件で `jikan list` を実行する。

**期待結果**：各行に ID、日付、タイトル、所要時間、プロジェクト名、タグ、状態を表示する。条件に合う記録だけが出て、表示した期間・分類条件と合計を確認できる。実行中記録は `Running` 等の文字列と経過時間で区別できる。

### EDT-01 / EDT-02：記録の編集と拒否

| ID | 操作 | 期待結果 |
| --- | --- | --- |
| EDT-01 | 完了済み #42 に開始・終了時刻、プロジェクト、タグを指定して `edit` | 正常終了し、変更後の主要項目を表示する。`view`/`list`/DB の値が指定内容と一致する。 |
| EDT-02 | 終了時刻が開始時刻より前になる変更、存在しないタグの追加 | 非 0 で終了し、理由を表示する。いずれも編集前の全フィールド・タグが保持される。 |

### RPT-01：期間レポートを集計する

**前提**：同一期間に次を作成する。`client-web` 60 分（`development`、`frontend`）、`jikan` 30 分（`review`）、プロジェクト・タグなし 15 分。

**操作**：対象期間を指定して `jikan report` を実行する。

**期待結果**：総計は 105 分。プロジェクト別は `client-web` 60 分、`jikan` 30 分、未分類 15 分で、合計は総計と一致する。タグ別は `development` 60 分、`frontend` 60 分、`review` 30 分、未分類 15 分で、重複計上のため総計と一致しない可能性を明示する。

### RPT-02：期間境界と空結果

**前提**：`Asia/Tokyo` で月末 `23:59:59`、翌月 `00:00:00` の記録を用意する。対象外の空期間も用意する。

**操作**：月次の `report --from --to` を実行し、続けて空期間を指定する。

**期待結果**：月末の記録だけが前月の対象になり、翌月の記録は含まれない。出力に適用期間とタイムゾーンを表示する。空期間は非エラーで、対象条件とデータがない旨を表示する。

### EXP-01：CSV を出力する

**前提**：RPT-01 の記録がある。

**操作**：同じ期間・分類条件で `jikan export --format csv` を実行する。

**期待結果**：CSV はヘッダー `id,start_at,end_at,duration,title,project,tags` を持つ。各行の対象・件数は同条件の `list` と一致し、開始・終了はタイムゾーン付き、タグは 1 フィールドに安全に格納される。説明文や装飾行を CSV 標準出力に混在させない。

## 6. 実装順と自動化の完了条件

第 1 段階では SET、STR、SWT、STS、STP、TMR を E2E 自動化の必須セットとする。第 2 段階で LST と EDT、第 3 段階で RPT と EXP を追加する。

各段階の完了条件は、該当する全シナリオが CI 上で安定して成功することに加え、失敗系で「エントリーが意図せず作成・停止・変更されていない」ことまで確認できることである。
